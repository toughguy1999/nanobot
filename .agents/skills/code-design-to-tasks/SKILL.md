## 工作流程

1. 阅读代码设计和相关代码，确认设计仍与仓库一致。
2. 按可独立实现、验证和交付的垂直功能拆分任务。
3. 根据依赖排序，在code_design同层新建tasks文件夹，输出 `{序号}-{任务名}.md`。
4. 检查任务之间没有遗漏、重叠或循环依赖。

## 信息边界

`code_design.md` 是技术方案的唯一事实来源。任务文档不得复制：

- 架构背景、现状概览和设计理由。
- 已在代码设计中完整定义的数据结构、流程图和伪代码。
- 通用项目规范和仓库架构。
- 可直接通过阅读目标代码获得的信息。
- 在多个任务中重复出现的验证命令。

需要使用设计细节时，通过路径和章节引用，例如：

> 依据 `../code_design.md#本地存储格式` 实现。

只有以下情况可以在任务中重复设计内容：

- 不重复会导致实现存在明显歧义。
- 这是容易遗漏的兼容性、安全性或数据迁移约束。
- 任务对原设计进行了明确修正；必须标记为“设计偏差”。

## 拆分原则

- 优先使用垂直切片，每个任务交付一个可验证的完整行为，不按数据库、API、UI、测试等技术层机械拆分。
- 一个小需求可以只生成一个任务。
- 高耦合且必须同时修改的内容放在同一任务。
- 可以独立实现、验证或回滚的内容才拆成不同任务。
- 测试通常与对应功能放在同一任务，不单独创建“补测试”任务。
